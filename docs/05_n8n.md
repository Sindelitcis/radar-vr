# Orquestração no n8n

**Projeto:** Radar VR
**Disciplina:** AI Factory, Etapas 1 e 2 (PUCPR)
**Versão do n8n:** 2.35.7

---

## 1. Papel do fluxo

O n8n agenda a edição, encadeia microsserviço, e-mail e alerta instantâneo, e
decide o caminho de cada item quando um passo falha.

A lógica do boletim continua em Python. Reimplementá-la em nós JavaScript
criaria duas fontes da mesma regra, com risco de divergirem. O fluxo faz o que
a ferramenta faz bem: agendamento, sequência, transporte de dados e desvio em
caso de erro.

## 2. Boletim personalizado (Etapa 2)

`n8n/fluxo_boletim_personalizado.json`

```
Executar manualmente ─┐
                      ├─► Gerar edição ─► Personalizar ─► Enviar boletim ─► Tem alerta ─► Enviar alerta
Agendamento 09h ──────┘        │          por assinante   por e-mail        urgente?      instantâneo
                               │               │               │                              │ erro
                               └───────┬───────┘               │ erro                         ▼
                                       ▼                       ▼                     Contingência:
                          Descrever indisponibilidade   Registrar falha              alerta por e-mail
                          → Gravar log local            do e-mail (/falha)
                          → Interromper execução
```

| Nó | Tipo | Função |
|---|---|---|
| Gerar edição | HTTP Request | `POST /edicao`; 2 tentativas, timeout de 10 min |
| Personalizar por assinante | HTTP Request | `POST /personalizar`; a resposta é uma lista e vira um item por assinante |
| Enviar boletim por e-mail | HTTP Request | `POST /enviar/email`; saída de erro ligada |
| Tem alerta urgente? | If | o envelope do assinante traz alerta instantâneo |
| Enviar alerta instantâneo | HTTP Request | `POST /enviar/instantaneo`, com o status do e-mail |
| Contingência: alerta por e-mail | HTTP Request | se o canal instantâneo falhar, o alerta segue por e-mail |
| Registrar falha do e-mail | HTTP Request | `POST /falha`, que avisa o operador |
| Descrever indisponibilidade → Gravar falha em log local → Interromper execução | Code, Convert to File, Read/Write File, Stop and Error | microsserviço fora do ar: registro em `logs/n8n_falhas.log` e execução encerrada como erro |

### Passagem de dados entre canais

Cada item carrega o envelope do assinante produzido por `/personalizar`. Os
nós seguintes leem o envelope pelo item pareado
(`$('Personalizar por assinante').item.json`), e não só a saída do nó
anterior:

- o alerta instantâneo cita o assunto do e-mail enviado minutos antes;
- o nó do alerta envia o status do e-mail (`email_status`); se o e-mail
  falhou, o serviço retira do alerta a referência a ele;
- a contingência monta o e-mail urgente a partir do texto do alerta que não
  foi entregue.

## 3. Tratamento de falhas

`n8n/fluxo_falhas.json`, configurado como *error workflow* do fluxo
principal.

```
Falha em qualquer execução ─► Descrever falha ─┬─► Avisar operador (POST /falha)
                                               └─► Converter em texto ─► Gravar em logs/n8n_falhas.log
```

O n8n dispara o *error workflow* só em execuções de produção (agendadas). Por
isso o fluxo principal também trata a indisponibilidade do serviço por conta
própria, pelas saídas de erro dos nós, o que vale para qualquer modo de
execução.

O registro local existe porque o aviso ao operador depende do próprio
microsserviço. Se ele estiver fora do ar, o arquivo é o único registro
possível.

## 4. Execução

```
executar_servico.cmd         sobe o microsserviço (envio real)
executar_servico.cmd teste   sobe em DRY_RUN: nada sai da máquina
executar_n8n.cmd import      importa os fluxos
executar_n8n.cmd run         executa o boletim personalizado
executar_n8n.cmd ui          abre a interface em http://localhost:5678
```

Com `RADAR_REAPROVEITAR_EDICAO=1`, o fluxo reenvia a edição atual sem coletar
de novo. Isso é útil para testar canais e contingências.

## 6. Configuração exigida pelo n8n 2

| Variável | Valor adotado | Motivo |
|---|---|---|
| `N8N_BLOCK_ENV_ACCESS_IN_NODE` | `false` | os fluxos leem o endereço do serviço e a pasta de logs por `$env`, sem valor fixo no JSON |
| `RADAR_SERVICO_URL` | `http://127.0.0.1:8765` | endereço do microsserviço |
| `RADAR_DIR_LOGS` | pasta `logs` do projeto | destino do registro local de falhas |
| `N8N_RESTRICT_FILE_ACCESS_TO` | pasta do projeto | o n8n grava o log de falhas; segue impedido de acessar qualquer outro caminho |
| `NODES_EXCLUDE` | `[]` | mantém o nó Execute Command do fluxo da Etapa 1 |

## 7. Fluxo da Etapa 1

`n8n/fluxo_radar_vr.json` permanece como registro: executava `jornal.py` por
Execute Command e lia o CSV publicado. Na Etapa 2, a chamada por HTTP
substitui a execução de comando no host, e o nó Execute Command deixa de ser
necessário no fluxo principal.
